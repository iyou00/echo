# Echo 成熟 Agent 产品路线与下一阶段实现方案

## 文档目的

本文回答两个问题：

1. Echo 要成为什么类型的 Agent 产品。
2. 下一阶段应该实现什么、按什么边界实现、如何判断完成。

本文是产品与工程之间的决策文档。后续 PRD、技术设计和任务拆分应与本文保持一致。

## 核心决策

Echo 的主线定位是：**关系型音乐 Agent**。

效率型音乐助手继续作为执行底座，负责准确理解点歌意图、找到可播放歌曲并完成播放。关系型 Agent 在此基础上维持跨入口、跨时间的情境连续性，判断何时说话、播放、追问或保持安静，并根据真实结果调整后续相处方式。

发生冲突时采用以下优先级：

1. 用户安全与明确要求。
2. 当前情境和阶段目标。
3. 已验证的近期反馈。
4. 长期偏好与陪伴风格。
5. Echo 的主动表达欲。

另一条“通用自主 Agent”路线暂不采用。Echo 不扩展为通用任务执行器，也不引入开放式多 Agent 协作。领域边界保持在音乐选择、播放、陪伴表达、音乐记忆和相关主动关心。

## 成熟 Agent 的定义

成熟的 Echo 应形成以下闭环：

```text
感知当前状态
  -> 判断是否需要介入
  -> 选择说话、询问、播放、调整或沉默
  -> 执行动作
  -> 观察真实结果
  -> 更新当前策略与长期理解
```

满足以下条件时，Echo 才算具备成熟 Agent 能力：

- 同一段生活情境能跨絮语、回声、播放和主动关心延续。
- 每次行动有明确原因、执行状态和结果，不把“推荐过”当成“听过”。
- 主动出现受到预算和反馈约束，沉默是合法行动。
- 能表达不确定性，必要时追问，执行失败时可恢复。
- 能识别关系失误并调整语气、主动程度和后续策略。
- 用户能查看、修正、暂停和删除关键记忆与主动行为。

## 产品原则

### 判断与执行分离

LLM 只承担判断类任务：

- 识别用户意图、情绪和阶段目标。
- 判断语气、介入强度和表达草稿。
- 从受限候选中提出行动建议。

确定性代码承担执行类任务：

- 路由、权限、状态转换和重试。
- 搜索、验证、播放、队列和持久化。
- 主动预算计算、安全边界和结果计数。
- 数据转换、去重、过期和冲突处理。

### 一个决策循环

下一阶段维持一个领域决策循环，由现有 runtime 协调服务执行。暂不增加多个相互对话的 Agent，也不增加开放式自主规划器。

### 证据强度分层

证据从弱到强依次为：

1. Echo 推荐了一首歌。
2. 歌曲成功开始播放。
3. 用户持续听了一段时间。
4. 用户听完、收藏或主动重播。
5. 用户明确评价或纠正。

高强度证据可以覆盖低强度推断。近期明确纠正优先于陈旧画像。

### 沉默是一种行动

Agent 每次都可以选择 `silence`。连续陪伴、低落情境和专注场景中的说话密度由决策策略控制，不能由“每轮必须生成回复”驱动。

## 三层状态模型

Echo 需要同时维护三种时间尺度，三者用途不同，不能混成一份画像。

### 当前状态

有效期通常为几分钟到数小时，例如：

- 正在加班、通勤、准备睡觉。
- 此刻疲惫、烦躁、兴奋或专注。
- 当前希望安静听歌，或希望有人聊天。

当前状态决定下一次行动。

### 阶段情境

有效期通常为数小时到数天，例如：

- 今晚的加班陪伴。
- 最近连续三天睡眠不好。
- 正在准备考试或处理一次项目交付。

阶段情境连接多个入口和多次会话，记录阶段目标、状态变化和已采取行动。

### 长期关系

有效期通常为数周以上，例如：

- 用户接受怎样的调侃。
- 用户在疲惫时更喜欢听歌、建议还是安静。
- 主动关心的接受程度。
- 稳定音乐偏好和明确禁区。

长期关系只能由重复行为或明确表达更新。

## 受限行动空间

每次决策只能从以下动作中选择：

| 动作 | 适用场景 | 必要约束 |
|---|---|---|
| `reply` | 用户明确聊天 | 不虚构事实或执行结果 |
| `clarify` | 目标或实体存在高风险歧义 | 一次只问关键问题 |
| `play` | 音乐目标明确 | 候选必须通过实体与可播放校验 |
| `adjust_music` | 当前歌曲方向不合适 | 保留用户最新约束 |
| `speak_then_play` | 回声或需要简短陪伴 | 说话密度服从当前状态 |
| `silent_play` | 用户专注或长时间连续陪伴 | 页面内容与当前歌曲保持一致 |
| `stay_silent` | 介入价值低或预算不足 | 记录决策，不生成文案 |
| `safety_guidance` | 明确身体或情绪风险 | 禁止调侃，建议现实支持 |

## 下一阶段范围

下一阶段只交付两个核心能力：

1. **连续情境**：让同一阶段状态跨絮语、回声、播放和主动关心延续。
2. **行动结果闭环**：让 Echo 知道行动是否真实执行、用户是否接受。

主动性预算先完成数据和决策接口，完整策略放到随后阶段。关系修复先记录必要信号，完整体验放到再下一阶段。

## 工作流 A：连续情境

### 目标

用户在一个入口表达的当前处境，可以被其他入口安全使用；新信息可以更新或结束旧情境。

### 核心对象

建议引入一个轻量的“阶段情境”记录，至少包含：

- `id`：阶段情境标识。
- `kind`：工作、休息、通勤、情绪陪伴等受控类型。
- `summary`：只包含有证据的事实摘要。
- `state`：当前情绪、精力和互动偏好。
- `goal`：本阶段希望获得的结果，例如专注陪伴或放松。
- `startedAt`、`lastActiveAt`、`endedAt`。
- `confidence`：状态判断置信度。
- `sourceEvidence`：支持该判断的对话或行为引用。

它与长期画像分开存储，也与单次连续回声 session 分开。回声 session 可以关联阶段情境，不能代替阶段情境。

### 更新策略

- 用户新表达优先更新当前状态。
- 明确恢复、结束或切换场景时结束旧情境。
- 长时间无活动后按类型过期，过期由代码计算。
- 多个候选情境冲突时保留证据更强、时间更新的一项。
- LLM 可以提议情境变化，确定性代码负责合并、过期和状态转换。

### 跨入口使用

- 絮语：创建或更新阶段情境。
- 回声：读取阶段目标，控制文案密度、歌曲方向和沉默比例。
- 播放：把实际播放结果回写到当前阶段。
- 主动关心：先判断情境是否仍有效，再决定是否介入。
- 风信：只使用已发生的事实，不把阶段推断写成长期人格结论。

### 验收场景

1. 用户在絮语说“今晚加班，脑子有点乱”，进入回声后无需重复说明。
2. 用户随后说“缓过来了”，严肃或高关怀模式能够结束。
3. 应用重启后，仍在有效期内的阶段情境可以恢复。
4. 已过期情境不会污染第二天的新对话。
5. 用户明确纠正情境后，所有入口采用最新信息。

## 工作流 B：行动结果闭环

### 目标

每个 Agent 行动都能回答：计划了什么、实际完成了什么、用户如何反应。

### 行动记录

每次重要行动形成一条可追踪记录：

- `actionId` 和关联的阶段情境。
- 决策动作和受控原因码。
- 计划目标，例如降低刺激、维持专注或改变能量方向。
- 执行状态：planned、started、succeeded、failed、canceled。
- 对应歌曲、口播或主动消息。
- 开始和完成时间。
- 失败类型与恢复结果。

自由文本理由用于产品调试，统计与策略必须使用受控原因码。

### 结果归因

结果归因由确定性事件完成：

- 播放成功只代表执行完成。
- 达到有效收听阈值形成弱正向结果。
- 听完、收藏、主动重播形成强正向结果。
- 快速切歌形成弱负向结果。
- 明确否定或纠正形成强负向结果。
- 播放失败属于系统失败，不能记为用户不喜欢。
- 页面关闭和用户主动停止属于中性或单独原因，不能自动判负。

### 策略更新

- 当前阶段策略可由一次强反馈立即更新。
- 长期偏好要求重复证据或明确表达。
- 行动结果只能更新它有权证明的维度。
- 同一次行为只能归因给一个主要行动，防止重复计数。

### 验收场景

1. 推荐后未播放的歌曲不会进入“用户听过”证据。
2. 播放接口失败不会降低歌曲或风格偏好。
3. 快速切歌能影响当前阶段的下一次选择。
4. 收藏和明确喜欢能形成更强证据。
5. 同一首歌跨队列、回声和聊天播放时不会重复归因。

## 随后阶段：主动性预算

主动行为使用确定性预算，不交给 LLM 自由决定触发频率。

预算输入包括：

- 距离上次交互和上次主动行为的时间。
- 当日主动次数。
- 最近主动行为是否被回应。
- 当前阶段是否适合被打断。
- 用户配置的主动程度和安静时段。
- 最近的关闭、忽略和静音行为。

预算输出只有：允许介入、延后、保持沉默。LLM 只在“允许介入”后判断内容和语气。

核心指标是“介入后悔度”：主动消息被忽略、立即关闭、关闭连续回声或明确表示不希望被打扰的比例。

## 随后阶段：关系修复

需要识别以下修复信号：

- 用户否定语气或调侃方式。
- 连续推荐跑偏。
- 用户明确不想聊或减少回复。
- Echo 对状态判断过重或过轻。

修复动作保持有限：承认偏差、降低主动程度、重新确认一个关键点、回到安静播放。修复结果进入关系证据，禁止用一条隐式行为永久改变人格。

## 用户控制

下一阶段需要预留以下控制边界：

- 暂停当前阶段情境。
- 结束连续陪伴。
- 关闭或降低主动关心。
- 修正 Echo 对当前状态的判断。
- 删除一条阶段记忆。
- 查看某次主动行为或推荐使用了哪些事实依据。

界面设计可以分阶段交付，数据层必须支持撤销和删除。

## 分阶段交付计划

### Phase 1：连续情境与结果闭环

交付内容：

- 阶段情境的数据契约、生命周期和跨入口读取。
- Agent 行动记录及执行状态。
- 播放、收藏、跳过、纠正与行动的单一归因。
- 情境过期、结束和用户修正。
- 关键路径测试和最小调试视图。

完成标准：本文两个核心工作流的全部验收场景通过，现有聊天、播放、回声、风信和画像行为保持兼容。

### Phase 2：受控主动性

交付内容：

- 主动预算和安静时段。
- 主动行为结果记录。
- `stay_silent` 决策。
- 主动程度设置和暂停控制。

完成标准：主动触发可解释、可限制、可暂停，并能根据近期负反馈自动收敛。

### Phase 3：关系修复与长期评估

交付内容：

- 语气与推荐偏差的修复策略。
- 陪伴风格的证据化更新。
- 长期质量指标和回归样本集。

完成标准：明确纠正能跨入口生效，关系偏好更新有证据边界，连续使用质量可以被量化。

## 工程落点

下一阶段沿用现有架构：

- runtime 负责行动生命周期、取消和错误分类。
- SQLite 负责阶段情境、行动和结果的本地持久化。
- chat、listening、playback、care pings 作为受控执行能力。
- renderer 只展示状态、结果和用户控制，不承载业务判断。
- LLM 输出结构化判断，服务层完成校验和执行。

新增能力应优先扩展现有边界。只有当同一生命周期逻辑被多个入口真实复用时，才引入新的共享模块。

## 测试策略

测试需要说明行为为什么重要，重点覆盖：

- 情境在入口间延续，同时按时过期。
- 新证据更新旧状态，明确纠正具有最高优先级。
- 行动执行失败与用户负反馈严格分离。
- 同一结果只归因一次。
- 主动预算耗尽后保持沉默。
- 高风险情境禁止调侃并维持安全策略。
- 用户结束、删除或暂停后，后续入口不再使用对应状态。

测试层级包括纯策略测试、数据库生命周期测试、跨服务契约测试和少量端到端关键场景。LLM 文案不做逐字断言，测试其结构约束、事实边界和行动选择。

## 评价指标

| 维度 | 核心指标 |
|---|---|
| 行动可靠性 | 搜索、播放、TTS、天气和主动通知的成功率 |
| 推荐接受度 | 有效收听率、听完率、收藏率、快速切歌率 |
| 理解准确度 | 追问率、纠正率、错误执行率 |
| 情境连续性 | 重复说明率、跨入口状态命中率、过期污染率 |
| 主动分寸 | 介入后悔度、主动回应率、静音与关闭率 |
| 长期信任 | 持续使用、主动表达状态、纠正后改善程度 |

指标用于发现策略问题，不能直接驱动单次人格表达。尤其不能为了提高回复率而增加打扰。

## 主要风险与控制

### 状态误判被长期保存

控制：阶段状态默认有过期时间；长期关系要求重复证据；用户纠正立即覆盖。

### 主动能力变成打扰

控制：确定性预算、安静时段、负反馈降频和 `stay_silent` 动作。

### 记忆越来越多但决策没有变好

控制：每类记忆必须声明可影响的决策维度，没有消费方的数据不进入核心状态。

### LLM 输出控制业务流程

控制：LLM 只提出受限判断；代码完成路由、状态转换、重试和持久化。

### 多入口重复执行

控制：所有重要行动具备唯一 `actionId`，结果只归因一次，入口共享同一行动状态。

## 下一步任务拆分原则

Phase 1 拆任务时按可独立验证的纵向闭环切分：

1. 阶段情境创建、更新、结束和过期。
2. 絮语写入情境，回声读取情境。
3. 行动记录与播放结果归因。
4. 用户纠正和删除传播到所有入口。
5. 风信和长期画像只消费符合证据强度的数据。

每个任务必须包含数据契约、业务规则、失败行为和验收测试。下一阶段不以增加 Prompt 数量、增加 Agent 数量或增加工具数量作为完成标志。
