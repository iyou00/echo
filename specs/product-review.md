# Echo 产品全角度评分报告

> 评审日期：2026-05-04（第三版）
> 评审版本：codex/sence 分支（含连续回声、上下文感知生成、场景推荐等改动）
> 评审角度：用户 / 全栈开发工程师 / 产品经理
> 核心命题：**Echo 会"越来越懂你"吗？**

---

## 本轮评审聚焦

前两版评审关注了架构、Onboarding、IPC 模块化等基础问题。本轮深入审查"理解"链路——从信号采集到口味档案到推荐引擎的完整管道，评估 Echo 的核心承诺是否兑现。

---

## 一、核心命题评估

### "懂你"链路设计

```
用户行为（播放/跳过/收藏/对话）
  → 信号采集（feedback.ts / chat.ts / playback.ts）
    → 口味档案（taste.ts — genres / artists / moods / portrait）
      → 推荐引擎（recommendation.ts — scoring + selection）
        → 用户听到新歌 → 新行为产生 → 循环
```

**理论闭环完整**，每一步都有对应代码。但管道有漏水点。

### 已经做到的 ✅

| 能力 | 实现方式 | 评价 |
|------|---------|------|
| 艺人偏好跟踪 | `applySignal()` 更新 artist affinity | 准确度尚可，但只有数值，没有"为什么喜欢" |
| 风格偏好 | genres 权重随行为调整 | 覆盖面够，但增量更新可能被批量重建覆盖 |
| 短期去重 | 120 首推荐 + 500 首播放记录冷却 | 对活跃用户有效，但对小库用户过于激进 |
| 语言偏好 | +4/-3 硬编码权重 | 粗暴但有效 |
| 行为闭环 | played/skipped/looped/favorited 都有处理 | 链路完整 |
| 口味提问 | `tasteQuestionScheduler` 主动提问 | 有创意，但捕获回答的可靠性待验证 |
| 连续回声上下文 | `<continuation>` 块注入 prompt | 新增功能，解决段落重复问题 |
| 场景推荐 | 5 个场景 + intent override | 有用但和口味档案不互通 |

### 做不到的 ❌

1. **理解"为什么"**：用户跳过一首歌，系统不知道是因为太快、太吵、还是不喜欢艺人。只知道"跳过了"
2. **情绪感知**：moods 维度是从播放历史统计出来的，不是实时感知的
3. **上下文推荐**：时间、天气传给了 LLM 文案生成，但推荐评分公式完全不看这些
4. **渐进式学习**：profile 重建会覆盖增量更新，"学"了但可能"记不住"
5. **个性化表达**：`echo_portrait` 是 LLM 生成的文本描述，但推荐引擎只看 genres/artists 数值，portrait 纯展示用

### 一句话结论

Echo 目前的"懂你"像一个朋友只记住了"你喜欢周杰伦、不喜欢王力宏"，但不知道你喜欢周杰伦的哪张专辑、什么心情下听、听的时候在做什么。**它有记忆，但没有理解。**

## 二、管道漏水点（按严重程度排序）

### P0 · `applySignal()` 太浅 — 只改数字，不改认知

**位置**：`taste.ts`（services）— `applySignal()`

这是 Echo 对用户行为做出反应的核心函数。接收 `played` / `skipped` / `looped` / `favorited` 等信号，但操作非常有限：

| 信号类型 | 实际操作 | 没做的 |
|---------|---------|-------|
| `favorited` | 对应 artist affinity +0.08 | 没更新 moods、没更新 scenes、没更新 energy 偏好 |
| `looped` | artist affinity +0.05 | 同上 |
| `played` | artist affinity +0.03 | 同上 |
| `skipped` | artist affinity -0.02 | 没分析"跳过原因"（风格？能量？语言？） |
| `unlike_artist` | artist affinity 直接清零 | 太粗暴，没有衰减机制 |

**用户影响**：连续听了一下午高能量电子乐，Echo 只记住了"你喜欢这些艺人"，没记住"你现在偏好高能量的东西"。晚上还是可能推慢歌。

---

### P0 · Profile 重建覆盖增量信号

**位置**：`taste.ts`（services）— `buildProfileFromTracks()` vs `applySignal()`

两条独立的口味更新路径：

1. **增量路径**：用户行为 → `applySignal()` → 直接修改 profile JSON
2. **批量路径**：某些时机触发 `buildProfileFromTracks()` → 从原始数据重建整个 profile

批量路径**完全覆盖**增量路径结果。用户今天 favorited 某艺人（affinity 0.6 → 0.68），明天 profile 重建后可能回到 0.6。

**用户影响**：偏好表达偶尔"丢失"。明明收藏了某个艺人，过两天推荐变回老样子。

---

### P1 · 推荐评分没有用语义数据

**位置**：`recommendation.ts` — `scoreCandidate()`

| 维度 | 是否使用 | 来源 |
|------|---------|------|
| 艺人匹配 | ✅ | taste profile artists |
| 风格匹配 | ✅ | taste profile genres |
| 语言匹配 | ✅ | 硬编码 +/- 3/4 分 |
| mood 匹配 | ⚠️ | 简单字符串匹配（+3） |
| scene 匹配 | ⚠️ | 同上（+2） |
| energy 偏好 | ❌ | 语义数据里有，评分没用 |
| tempo 偏好 | ❌ | 语义数据里有，评分没用 |
| familiarity 偏好 | ❌ | 语义数据里有，评分没用 |

系统花大量精力收集 track semantics（language、genres、moods、scenes、energy、tempo、familiarity），但推荐评分只用 genres/artists 文本匹配。energy/tempo/familiarity 完全没进入评分公式。

**用户影响**：Echo 知道你常听"中速、中等能量"的中文流行，但推荐时完全不考虑速度和能量，只匹配风格和艺人。可能推一首同风格但 BPM 180 的歌。

---

### P1 · 冷却区对小音乐库过于激进

**位置**：`listening.ts` — `recentBlockedKeys()`

```ts
const keys = trackIdentitySet([
  ...loadRecentRecommendedTracks(120),   // 最近 120 首推荐
  ...loadListenedTracksSince(24, 500),   // 24h 内 500 首
])
```

活跃用户 24h 可能听 50-80 首，加上 120 首历史推荐，冷却池 200+ 首。音乐库 200-300 首的用户，候选池被砍到所剩无几，频繁走到 fallback。

**用户影响**：小库用户反复看到"我现在还没摸清你的歌单"这类 fallback 文案。

---

### P1 · Direction Memory 名不副实

**位置**：`recommendation.ts` — `directionMemoryScore()`

所谓"方向记忆"实际是 `compactText()` 压缩歌名后做**字符串包含检查**。用户说"更多像这样的"，系统检查候选歌名是否和目标歌名有文本重叠。这不是语义相似度，是字符串匹配。

用户要的是风格/情绪/能量相似，不是歌名相似。

---

### P2 · 对话信号提取覆盖面窄

**位置**：`chat.ts` — `inferTasteSignal()`

用正则提取口味信号：
- `"我喜欢(.*?)的"` → like_artist
- `"我不太听|我不喜欢"` → unlike_artist

覆盖面很窄。以下表达全部被忽略：
- "最近想听点安静的"（mood 信号）
- "有没有那种开车时候听的"（scene 信号）
- "不太想听英文歌了"（language 信号）
- "来点轻松的"（energy 信号）

---

### P2 · 回声 fallback 文案暴露内部状态

**位置**：`listening.ts` — `fallbackText()`

> "我现在还没摸清你的歌单，所以先不硬推歌。"

用户不应该看到系统的内部状态。这句话的潜台词是"系统还没准备好"，会让用户对产品失去信心。应该用更自然的表达，比如"今天先不急，你先听点什么"。

## 三、用户视角评分

**总分：7.8 / 10（上版 7.9 → -0.1）**

| 首次上手门槛 | 6.5 | 6.5 | 不变 |
| 功能可发现性 | 5.5 | 5.5 | 不变 |
| 情感共鸣 | 9 | 9 | 不变 |
| 日常使用粘性 | 7.5 | 7.5 | 不变 |

### 连续回声体验评价（新增功能）

**做得好的地方：**
- `<continuation>` 块让连续段落有层次感，不再重复
- 连续失败 2 次后自动停止，不会无限循环报错
- 音乐播完自动触发下一段，体验流畅

**体验问题：**
- 无 skip 按钮，必须听完或等完当前 TTS
- "再来一次"按钮只有 disabled，没有 loading 视觉变化
- 连续回声失败时 `setVoiceContinuous(false)` 但 UI 没解释为什么停了
- 2 秒 fallback timer 在没有音乐启动时触发，但用户感知上可能太快（刚说完就又说）

### 场景推荐体验评价

- 5 个场景覆盖了常见需求（专注/犯困/放松/烦躁/随机）
- 2 小时 TTL 合理
- 但用户不知道当前处于什么场景，也不知道场景什么时候结束

## 四、工程师视角评分

**总分：8.0 / 10（与上版持平）**

| 维度 | 上版 | 本轮 | 变化原因 |
|------|------|------|----------|
| 架构设计 | 9 | 9 | 不变 |
| 技术选型 | 8 | 8 | 不变 |
| 可维护性 | 8.5 | 8.5 | 不变 |
| 代码可测试性 | 5.5 | 5.5 | 不变 |
| 错误处理 | 7 | 7.5 | 连续回声的错误处理更完善 |
| 性能 | 7 | 7 | 不变 |

### 新增代码质量

**连续回声实现**：`speakingLockRef` 同步锁 + `fadeVolumeRef` 防重入 + `musicStartedRef` 音乐状态追踪，三层防御解决竞态问题。这是本次改动中工程质量最高的部分。

**上下文感知生成**：`continuation` 参数从 Voice.tsx → preload → IPC → listening.ts 全链路透传，没有遗漏。`<continuation>` 块利用已有的 `recentScenarios[0]`，不引入新状态管理，设计简洁。

### 仍存在的工程风险

1. **`listening.ts` 模块级状态**：`recentScenarios` / `recentTrackKeys` 在主进程内存中，重启丢失。连续回声的上下文无法跨重启恢复
2. **`recommendation.ts` 1226 行**：单文件过长，intent 解析、候选获取、评分、选择应拆分
3. **IPC 类型安全**：preload ↔ types/ipc ↔ api.ts 参数类型依赖手写对齐，没有编译时保证
4. **Voice.tsx 14 个 refs**：复杂度高，但受限于音频 API 的命令式特性，难以避免
5. **`applySignal()` 多分支**：多个 if-else 处理不同 signal 类型，适合改为策略模式

### 推荐引擎的 LLM 调用链

一次完整推荐最多 3 次 LLM 调用：
1. `inferIntentWithLlm()` — 意图解析（4s 超时）
2. NetEase API — 获取候选
3. `selectWithLlm()` — 最终选择

加上 `generateListeningSegment()` 的文案生成 LLM 调用，回声场景一次完整流程最多 4 次 LLM 调用。延迟敏感场景需要注意。

## 五、产品经理视角评分

**总分：7.5 / 10（新增视角）**

| 维度 | 得分 | 说明 |
|------|------|------|
| 核心价值清晰度 | 9 | "AI 音乐陪伴"定位准确 |
| 用户价值兑现 | 7 | 框架在，但"懂你"效果打折 |
| 冷启动策略 | 6 | Onboarding 有了，但缺跳过路径 |
| 长期留存设计 | 7 | 口味提问/风信/场景有层次，但反馈闭环弱 |
| 用户反馈感知 | 5 | 行为训练不可见，用户不知道系统在学什么 |
| 数据驱动验证 | 4 | 没有推荐效果追踪，无法量化"懂你"进展 |

### 产品设计缺陷

1. **没有推荐效果追踪**：不知道推荐接受率（播放/跳过比）是否随使用时间提升。无法量化"懂你"是否在进步
2. **行为训练不可见**：用户切歌、收藏时没有任何反馈，不知道这些行为在训练 Echo。错失了建立信任的机会
3. **口味提问可能打断对话**：最少 2 轮后提问，但如果对话只有 3 轮，第 3 轮突然问口味问题会突兀
4. **场景系统孤立**：场景和口味档案不互通，场景推荐不看口味数据
5. **`echo_portrait` 纯展示**：LLM 生成的口味画像文字，推荐引擎完全不看

### 长期留存隐患

| 使用阶段 | 用户感受 | 风险 |
|---------|---------|------|
| Day 1 | 新奇，Echo 会说话会推歌 | Onboarding 卡住（没歌单）|
| Week 1 | 推荐"还行"，对话有意思 | 口味信号太浅，推荐改进不明显 |
| Month 1 | 推荐开始重复，感觉"就那样" | 冷却区 + 候选池枯竭 |
| Month 3 | 不确定 Echo 有没有变聪明 | 无量化指标，无可见进展 |

核心问题：用户无法感知 Echo 在"变聪明"，因为：
1. 推荐改进缓慢（信号太浅）
2. 改进了用户也看不到（行为训练不可见）
3. 没有量化指标展示进展

## 七、优先级建议

### P0 — 核心价值必须补齐

1. **`applySignal()` 增量更新 moods/scenes/energy 维度** — 让行为真正改变推荐，不只是改艺人 affinity。用户循环一首高能量电子乐，moods 和 energy 偏好应该同步变化
2. **解决 profile 重建覆盖增量信号** — 要么让 `buildProfileFromTracks()` 考虑已有的 `applySignal()` 修改，要么让增量信号写入独立于 profile 的数据源
3. **回声 fallback 文案重写** — 不暴露系统内部状态。将"我现在还没摸清你的歌单"改为自然表达

### P1 — 推荐"感觉对"

4. **推荐评分引入 energy/tempo 维度** — 让推荐不只是"风格对"而是"感觉对"。数据已经有了，只差接入评分公式
5. **降低冷却区对小库的影响** — 冷却池空时放宽过滤条件，或对 fallback 候选降低门槛
6. **行为训练可见化** — 切歌时轻提示"记住了，这个方向先放放"；收藏时"喜欢这首，我记下来了"。让用户感知 Echo 在学习
7. **场景和口味联动** — 场景推荐参考口味数据，场景 intent override 使用 taste profile

### P2 — 提升"懂你"深度

8. **`directionMemoryScore()` 改为基于语义的相似度** — 用 track semantics 的 moods/energy/genres 向量计算，而不是歌名字符串匹配
9. **对话信号提取扩大覆盖面** — 捕获 mood/scene/language/energy 维度的偏好表达，不限于艺人名
10. **口味统一服务层** — 解决 taste/feedback/tracks/semantics 状态分散、路径冲突的问题
11. **推荐效果追踪** — 记录每日推荐接受率，量化"懂你"进展，也用于产品数据驱动

### P3 — 体验打磨

12. **首次使用引导完善** — 加跳过路径，加完成反馈
13. **回声页面 UX** — skip 按钮、loading 状态、连续失败说明
14. **场景状态可视化** — 让用户知道当前场景和剩余时间

---

## 八、一句话总结

Echo 的"懂你"框架是完整的——从信号采集到口味档案到推荐引擎的闭环已经搭好。但管道有漏水：信号太浅（只改艺人 affinity 不改认知）、增量更新可能被覆盖、推荐评分浪费了已收集的语义数据。**补上这些漏水点，"懂你"的效果会质变。** 下一步核心动作：让 `applySignal()` 真正影响 moods/scenes/energy 维度，让推荐评分使用已有的语义数据。
