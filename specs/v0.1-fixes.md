## 修复 1 · Echo 推荐的歌曲,播放的不是这个

### 问题描述

用户让 Echo 推荐歌曲,Echo 在文字里说出的歌名/艺人是对的,但点击 track card 播放后,响起的是另一首歌。

### 根因分析(我们的 spec 在这里有歧义)

`features/recommendation.md` 的双工具流程:

```
LLM 调 find_tracks(vibe: "...")
   → recommender.ts 返回 [{ ref: 'C1', title, artist }, ...]
LLM 调 play_tracks({ ref: 'C2' })
   → 主进程必须把 'C2' 这个 ref 映射回真实 trackId
```

最可能的 bug:**recommender.ts 没有持久化候选池**。LLM 第二次调用 `play_tracks` 时,第一次的 `[C1, C2, C3]` 已经被 GC 或 ref 表混乱,导致:
- 拿 `'C2'` 字符串当歌名直接去网易云搜 → 搜到一首随便的歌
- 或反查到上一次会话的 C2 → 张冠李戴

### 修复方案

#### 1.1 候选池必须挂在会话级别的 Map 上

```typescript
// src/main/services/recommender.ts

// 模块级 Map · 按 sessionId(或 conversationId)隔离
const candidatePools = new Map<string, Map<string, Track>>();

export async function findTracks(sessionId: string, query: FindTracksInput) {
  const ranked = doFind(query); // 检索 + 排序逻辑保持
  
  // 保存这次的候选,key = ref,value = 完整 Track
  const pool = new Map<string, Track>();
  ranked.forEach((t, i) => {
    const ref = `C${i + 1}`;
    pool.set(ref, t);
  });
  candidatePools.set(sessionId, pool);
  
  return ranked.map((t, i) => ({
    ref: `C${i + 1}`,
    title: t.title,
    artist: t.artist,
    year: t.year,
    vibeMatch: t.score,
    hint: t.hint,
  }));
}

export function resolveRef(sessionId: string, ref: string): Track | null {
  return candidatePools.get(sessionId)?.get(ref) ?? null;
}
```

#### 1.2 play_tracks 严格走 ref 反查 + 兜底

```typescript
// 在 chat.ts 处理 play_tracks 工具调用时

async function handlePlayTracks(sessionId: string, llmInput: { tracks: { ref: string; note?: string }[] }) {
  const tracks: ResolvedTrack[] = [];
  
  for (const { ref, note } of llmInput.tracks) {
    // 正路:从候选池反查
    let track = recommender.resolveRef(sessionId, ref);
    
    if (!track) {
      // 兜底:LLM 已经在前一步看到过 candidates 的 title/artist
      // 如果 ref 失效,从 LLM 这一轮的 message context 里捞最近的 find_tracks 工具结果
      const lastCandidates = extractLastFindTracksResult(sessionId);
      track = lastCandidates?.find(c => c.ref === ref) ?? null;
    }
    
    if (!track) {
      // 真的找不到 · log + 用户友好提示
      console.warn('[recommender] ref resolve failed', { sessionId, ref });
      tracks.push({ status: 'unresolved', ref, note });
      continue;
    }
    
    // 拿到 Track 后,v0.1 不真播放,只渲染 card
    // v0.2 起:走 netease searchTrack(track.title, track.artist) 拿播放链接
    tracks.push({
      status: 'ready',
      title: track.title,
      artist: track.artist,
      year: track.year,
      note,
      // 真实 trackId/播放链接 · v0.2 填
    });
  }
  
  return tracks;
}
```

#### 1.3 关键约束(写到代码注释里,防止 AI 后续优化时改坏)

```typescript
// ⚠️ 不要把 ref 字符串当作歌名/搜索关键词使用
// ⚠️ ref 是临时引用,只在 candidatePools 里有意义
// ⚠️ 候选池必须按 sessionId 隔离,不能共享
```

### 验收

测试场景:
1. 让 Echo 推 3 首慢歌 → 候选池里有 C1/C2/C3 三个真实 Track
2. 用户点第二张 card 播放 → console 里看到 `resolveRef('C2')` 返回正确的 title/artist
3. 用户在同一会话里再问"再推几首类似的" → 新候选 D1/D2/D3,旧的 C 系列还能反查到
4. 关 app 重开 → 候选池清空(候选不持久化),用户点旧 card 弹友好提示"这首我得重新找一下"

## 修复 2 · 列表 · 改为"今日推荐流"模型

### 问题描述

用户期望:**列表页"正在播放"区应该自动显示今天 Echo 推荐过的所有歌**(包括正在播的、还没播的、已播的),按"最新推荐排在最上面"排序。当前实现是"用户手动点过的才进队列"。

### 概念修正(重要 · 写给开发 AI)

**Echo 这个产品没有"用户主动点歌 vs Echo 推荐"的区分**。
**所有播放都是从对话来的**——用户说"放点慢的",LLM 调推荐工具,Echo 推一首,用户点 card 播放。
**所以"队列"就等于"今天 Echo 推过的所有歌"**。

### 修复方案

#### 2.1 数据模型 · 增加 `today_queue` 概念

不需要新表。复用 `tracks_listened` + 一个内存视图:

```typescript
// 概念:
interface TodayQueue {
  date: string;                // "2026-04-25"
  items: TodayQueueItem[];
}

interface TodayQueueItem {
  // 来自 Echo 推荐的元数据
  recommendedAt: string;       // ISO 时间,用来排序
  title: string;
  artist: string;
  echoNote?: string;           // Echo 给的小注
  refSession: string;          // 哪次对话推的(便于跳回上下文)
  
  // 播放状态
  status: 'pending' | 'playing' | 'completed' | 'skipped';
  playedAt?: string;
  position?: number;           // 上次播放位置(秒),用于断点续播 · v0.2
}
```

#### 2.2 写入时机

**只要 LLM 调 `play_tracks` 成功**(即使用户没点播放按钮),就**立即**把它加入今日队列,状态 = `pending`。

```typescript
// chat.ts 处理 play_tracks 后
for (const track of resolvedTracks) {
  await todayQueue.add({
    recommendedAt: new Date().toISOString(),
    title: track.title,
    artist: track.artist,
    echoNote: track.note,
    refSession: sessionId,
    status: 'pending',
  });
}
```

**用户点 card 播放** → status: pending → playing
**听完(>= 80%)** → playing → completed
**切歌** → playing → skipped

#### 2.3 列表 UI 改造

`Queue.tsx` "正在播放"tab 显示逻辑:

```
按 recommendedAt 倒序排列(最新推荐在最上面)

[正在播放的歌] · 高亮 · 顶部置顶(如果 status === 'playing')

[pending 状态的歌]    · 正常显示
[completed 状态的歌]  · 灰色 50% 透明度,但仍可点击重播
[skipped 状态的歌]    · 灰色 30% 透明度,小字标"你切了"
```

视觉上参考 `design/queue.html`,但加一个**状态徽章**(右上角小圆点):
- 绿色实心 = playing
- 主色描边 = pending
- 灰色 = completed
- 灰色横线 = skipped

#### 2.4 当天的定义

**自然日**(00:00 - 23:59 本地时区)。

每天 0 点定时任务:
- 把昨天的 today_queue 物化到 `tracks_listened` 表(已有 schema)
- 清空内存里的 today_queue,新的一天从空开始

如果用户跨日还在用 app(比如凌晨 1 点):
- 凌晨 0 点触发归档时,如果当前正在播一首歌 → 那首歌**结算到昨天**(因为它是昨天推荐的),今天从空开始

#### 2.5 历史推荐 · 二级 tab

`Queue.tsx` 的 tab 结构:

```
[正在播放] [Echo 备选] [收藏] [过往]
                                  ↑ 新增
```

点 "过往" 进入二级视图:

```
2026-04-24  · 7 首
  ┌───────────────────────────────┐
  │ 林俊杰 · 不为谁而作的歌       │  ← 已听完
  │ 海洋Bo · 向云端                │  ← 已听完
  │ Charlie Puth · Attention       │  ← 切了
  │ ...                            │
  └───────────────────────────────┘

2026-04-23  · 5 首
  [...]

2026-04-22  · 3 首
  [...]
```

按日期分组,每组可点击展开/收起,**每首带当时 Echo 给的小注**。

UI 参考 `design/yinyi.html` 的"翻页"感——这个"过往"列表也是 Echo 的另一种"日记",只是日记的内容是歌而不是文字。

### 验收

1. 让 Echo 推 3 首歌 → 列表页"正在播放" tab 立刻看到 3 首 pending
2. 点最上面那首播放 → 它变 playing,加播放指示器,其他保持 pending
3. 听完一首 → 变 completed,灰色,沉到下面,新一首接上播
4. 切歌 → 变 skipped 灰色横线
5. 凌晨 0 点后再看 → 列表清空,昨天的迁移到"过往"
6. 点"过往" → 看到按日期分组的历史

## 修复 3 · 新增 · "日封" Day Seal 机制

### 这是新增功能,不是修复

**产品概念**:用户关 app 时,Echo 把今天的对话封存成一个 .md 文件。下次打开时,Echo 不带着昨天的对话原文,而是带着昨天的"摘要"作为内心知识——表现是**新对话默认空白,Echo 主动用一句话延续昨天**。

### 与"音忆"的区别(重要 · 不要混淆)

| | 音忆 (yinyi) | 日封 (day_seal) |
|---|---|---|
| 写给谁 | 用户看 | Echo 自己用 |
| 风格 | 衬线日记,有情感 | 结构化摘要 |
| 时机 | 每晚 22:00 | 关 app 时 |
| 存储 | SQLite `yinyi` 表 | 文件:`data/seals/YYYY-MM-DD.md` |
| 长度 | 200-350 字 | 200 字摘要 + 元数据 |
| 用户能改吗 | 不能 | **能**(就是普通 md 文件) |

### 实现细节

#### 3.1 触发条件

```typescript
// main/index.ts
app.on('before-quit', async (e) => {
  e.preventDefault();
  await daySeal.archive();  // 归档当天对话
  app.exit();
});

app.on('window-all-closed', async () => {
  // 关闭主窗口时也归档(因为 Echo 会"最小化到托盘"继续跑)
  // 但不退出 app · 只归档
  await daySeal.archive();
});
```

注意:**主窗口关闭 ≠ app 退出**(我们之前的设计是关窗口最小化到托盘)。所以:
- 主窗口关闭时归档当天 → 下次打开窗口,显示"今天还在,但之前那段我封存了"
- 真正 app 退出时再归档一次(防止漏)

考虑到归档可能跨多次,加个**幂等性**:同一天的 seal 文件,**追加而不是覆盖**(用户可能下午关一次、晚上又关一次,合并所有片段)。

#### 3.3 生成流程

```typescript
// services/daySeal.ts
async function archive() {
  const today = todayDate();
  const sealPath = `data/seals/${today}.md`;
  
  // 收集素材
  const conversations = await db.conversations.getToday();
  if (conversations.length === 0) return; // 今天没对话,不归档
  
  const tracks = await db.tracksListened.getToday();
  const taste = await db.taste.getProfile();
  const events = await db.events.getActive();
  const yinyi = await db.yinyi.getByDate(today); // 如果已经有音忆
  
  // 调 LLM 生成结构化摘要(用专门的 prompt)
  const seal = await llm.generateSeal({
    conversations,
    tracks,
    taste,
    events,
    yinyi,
  });
  
  // 写文件(幂等:如果文件已存在,合并而不是覆盖)
  if (existsSync(sealPath)) {
    await mergeSeal(sealPath, seal);
  } else {
    await writeMarkdown(sealPath, seal);
  }
  
  // 同时执行的副作用:
  // 1. 应用 seal.markings 到 taste_profile / events
  // 2. 截断 conversations 表里今天的对话(可选 · 默认不删,只标 archived=true)
}
```

#### 4.6 进入听音 tab 后的初始状态

不要进了就自动开始 LLM 生成。先显示一个**待机态**:

```
+--------------------------------+
|  E C H O · S T A N D B Y      |
|                                |
|      让我说一段?               |
|                                |
|     ┌─ 让 Echo 说话 ─┐         |
|                                |
|  (背景是抹茶绿但比 SPEAKING 浅)|
+--------------------------------+
```

用户点"让 Echo 说话"按钮 → 触发 LLM 生成 → 进入 SPEAKING 状态。

这样:
- 用户进 tab 不会被突然的语音吓到
- 不浪费 LLM token(没人想听就不生成)
- 用户能主动控制"我现在想听 Echo 说一段"

### 验收

1. 主界面顶栏看到三个 tab:音忆 / 听音 / 列表(等宽字 + 字距)
2. 输入框旁边只有发送和取消,没有语音按钮
3. 点"听音" → 进抹茶绿页面 · 中央显示"让我说一段?" + 一个按钮
4. 点按钮 → 状态变 THINKING → 几秒后 SPEAKING + 文字三段着色 + 音浪
5. 说完显示 DONE + "再说一段"按钮
6. 顶栏左侧 `◁ 返回` 能返回主对话
7. 在听音页时,底部 mini player 还在(如果有歌在播)
